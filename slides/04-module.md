# Модуль — кирпичик со стандартной формой

У любого модуля одинаковый «разъём»: **название + параметры желаемого состояния**. Поэтому модули стыкуются друг с другом, как кирпичи в кладке.

**`одна задача (task)`**

```yaml
- name: Пользователь для деплоя   # зачем мы это делаем
  ansible.builtin.user:             # какой кирпичик берём
    name: deploy                    # параметры
    shell: /bin/bash                #   желаемого
    state: present                  #   состояния
```

> 💡 **Аналогия.** Кирпичу не важно, будет он частью гаража или собора. Модулю `user` тоже не важно, для чего нужен пользователь: для веб-сервера или для базы. **Смысл появляется, когда кирпичики сложены вместе.**

> [!NOTE]
> Инструкция к любому кирпичику: `ansible-doc ansible.builtin.user`

| Сущность | Что это и зачем |
|---|---|
| name — подпись задачи | Человекочитаемое «зачем». Её видно в выводе при запуске. |
| Параметры — желаемое состояние | Что должно быть в итоге: какой пользователь, с какой оболочкой, существует ли он. |

**Внутри модуля `ansible.builtin.user`:**
1. **Посмотреть** как сейчас на сервере
2. **Сравнить** с желаемым состоянием
3. **Изменить** только разницу

Результат: `ok — уже как надо` · `changed — исправил` · `failed — не смог`

<details><summary>🎤 Заметки лектора</summary>

Разобрать задачу по частям, пролистывая стрелкой: подпись, модуль, параметры.

Самое важное — что происходит внутри модуля: он не просто выполняет команду, а сначала смотрит на сервер, сравнивает с желаемым и меняет только разницу. Это и делает модуль «умным кирпичом».

Три исхода: ok (уже было как надо), changed (что-то исправил), failed (не смог). Студенты видели их в прошлый раз в выводе — теперь понятно, откуда они берутся.

</details>
